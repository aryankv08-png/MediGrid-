2. Zero Double-Allocation Concurrency Model Strict Two-Tier Locking

In an emergency surge, hundreds of ambulances may seek the last available ICU bed across multiple application nodes simultaneously. MediGrid implements a mathematically proven two-tier locking strategy that guarantees zero double-allocations even under intense race conditions:

1
Tier 1: Redis Distributed Mutex (Fast Boundary Lock)
Before querying or reserving candidate beds, the instance attempts to acquire an exclusive distributed lock using a cryptographic token: 
SET lock:hospital:{hospitalId} {token} NX EX 5
If another instance holds the lock, the competing request yields and backs off, preventing parallel read-modify-write collisions.
2
Tier 2: MySQL Optimistic Concurrency Control (OCC) with Atomic Versioning
Even if a distributed lock expires or degrades during network partitions, MySQL executes an atomic compare-and-swap update: 
UPDATE beds 
SET status = 'RESERVED', assigned_actor = ?, reservation_expires_at = NOW() + INTERVAL 15 MINUTE, version = version + 1
WHERE id = ? AND status = 'FREE' AND version = ?;
If affectedRows === 0, the transaction immediately detects race contention, rolls back, and automatically selects the next suitable candidate hospital.
3
Safe Token-Verified Release via Atomic Lua Script
To prevent accidental unlock of a key that expired and was re-acquired by another node, release is strictly guarded by Lua: 
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
3. Inter-Hospital Transfer Saga Workflow Compensating Rollback Engine

Transfers between hospitals require distributed transaction guarantees without blocking two-phase commit (2PC) bottlenecks. MediGrid uses an asynchronous Saga orchestrator with automatic timeout compensation:

A
Step 1: REQUEST_TRANSFER (Forward Action)
Source hospital staff initiates transfer. The orchestrator checks receiving hospital capacity, reserves a bed at the destination with a 15-minute countdown, publishes transfer.requested to RabbitMQ, and records the Saga state in MySQL.
B
Step 2: ACCEPT_TRANSFER (Commit Action)
Receiving hospital console displays a prominent countdown alert with one-click Accept/Decline. Upon acceptance, destination bed is committed to RESERVED, ambulance is dispatched, and Saga marks step as ACCEPTED.
C
Step 3: REJECT_TRANSFER / TIMEOUT (Compensating Rollback Action)
If the receiving hospital rejects the patient or the countdown expires without response, the Saga orchestrator automatically executes compensation: the reserved bed at the target hospital is reverted to FREE, the source hospital is alerted in real-time via WebSocket, and the Saga is closed as ROLLED_BACK.
4. RabbitMQ Priority Queuing & Dead Letter Handling Preemption & Poison-Message Isolation
Priority Preemption (10 vs 0)
Emergency bed requests with priority CRITICAL are flagged with AMQP priority 10. Even if 10,000 routine administrative bed updates are queued, the broker dispatches the critical message first with zero latency head-of-line blocking.
Dead Letter Exchange (DLX)
Messages rejected without acknowledgement (basic.nack(requeue: false)) or exceeding maximum retry limits are redirected by the broker to medigrid.dlx and held in medigrid.queue.dead_letter for operator audit.
Publisher Confirms
Every critical bed state change is published using confirm channels (channel.publish(..., { persistent: true })), ensuring zero message loss across broker restarts or hardware failures.
